# تشغيل المشروع على Hostinger مع MySQL

تم تجهيز قاعدة `u498439850_alar` فعليًا بتاريخ 3 أكتوبر 2026. الإصدار المقاس هو MariaDB 11.8.9؛ يتصل به Prisma عبر موصل MySQL/MariaDB. أُضيفت ترحيلات التجارة والمسابقات حتى 006، وأصبحت العلاقات 58 مع 4 triggers. بقي حساب المالك السابق والمنتجات العشرة وصورها محفوظة، ونُشرت المنتجات التوضيحية العشرة لاحقًا بطلب المالك دون تعديل الأسعار أو المخزون. حالة إصلاح نشر التطبيق موثقة في `HOSTING-REPAIR.md`.

## ما يعمل

الدخول والجلسات وتغيير كلمة المرور والصلاحيات وسجل العمليات؛ تحرير المنتجات بالعربية والإنجليزية ومعاينتها ونشرها وأرشفتها؛ الأسعار Decimal؛ العلامات والتصنيفات وتعريفات فلاتر المواصفات؛ معلومات المتجر وواتساب والأسئلة والضمان والتجهيزات؛ رفع الصور وترتيبها وحذف الصور غير المستخدمة. الموقع يقرأ المحتوى من API ويعرض المنتجات المنشورة فقط، مع تحميل وخطأ وإعادة محاولة. تحديث البيانات لا يتطلب إعادة البناء، وتُحدّث البيانات عند عودة التركيز وبفاصل دقيقة.

المنتجات المستوردة أمثلة وليست مخزونًا مؤكدًا؛ تظهر منشورة بوسم «منتج توضيحي» وسعر غير محدد ومخزون غير مراجع. أرقام الهاتف وواتساب الأصلية فارغة. أدخل معلومات المتجر وتحقق من الصور والمواصفات قبل النشر. إدارة التجارة والسلة وحسابات العملاء والطلبات موثقة في `COMMERCE.md`. لا يُحجز المخزون؛ الخصم عند إكمال البيع بواسطة الإدارة فقط.

## محليًا

لفتح نسخة البناء على هذا الجهاز: `npm run start:local` ثم `http://127.0.0.1:53000/admin/`. هذا الأمر يخدم الواجهتين بإعداد HTTP محلي، ويستخدم قاعدة تطوير محلية منفصلة من `.env` ويرفض قاعدة بعيدة. المصدر السحابي وتاريخ بيانات التطوير وحزمة الرفع موثقة في `CLOUD-LOCAL.md`. اتركه يعمل أثناء الاستخدام. الأمر `npm start` مخصص لإعداد الإنتاج الذي يتطلب HTTPS؛ لا تستخدمه للدخول عبر HTTP المحلي.

استخدم Node.js 24، وMySQL 8.4 أو MariaDB 10.4 فأحدث. من جذر `lenis`:

```sh
npm ci
npm run env:init
npm run db:generate
npm run build -w @aljeel/shared
docker compose -f docker-compose.dev.yml up -d
npm run db:migrate
npm run db:audit:protect
npm run db:import
npm run seed:owner
```

أمر المالك تفاعلي دون كلمة مرور ثابتة؛ لا تشغله لإعادة إنشاء المالك المستورد. شغّل `dev:server` و`dev:admin` و`dev` في نوافذ منفصلة. الإدارة على `http://localhost:5174/admin/` والمتجر على المنفذ 5173 والخادم على 3000. في جهاز Windows الحالي يمكن استخدام `npm run dev:local`؛ يشغّل MariaDB الموجود في Laragon ببيانات مستقلة داخل `.local/mariadb` على 53307. يمكن تعيين `MYSQL_BIN` لمسار binary مناسب. هذا خيار تطوير، وليس متطلب إنتاج.

## إعداد Hostinger

المراجع الرسمية: [نشر Node.js](https://www.hostinger.com/support/how-to-deploy-a-nodejs-website-in-hostinger/)، [ربط MySQL](https://www.hostinger.com/support/connecting-a-hostinger-mysql-database-to-a-node-js-application/)، [مشاكل البناء](https://www.hostinger.com/support/fix-failed-to-build-application-error-hostinger-node-js/).

1. خذ نسخة احتياطية قبل كل تحديث. في hPanel أنشئ Node.js Web App واختر Node.js 24 وإعداد Other/Custom؛ إعداد Fastify الافتراضي في هذه اللوحة لا ينفذ أمر البناء.
2. ارفع المشروع من جذر `lenis` عبر ZIP أو GitHub. استبعد `node_modules` و`.local` و`.backups` وملفات `.env` وملفات المتصفح في `review`. يحتاج البناء مجلدات `src` و`public` و`admin` و`server` و`packages` والملفات الجذرية وlockfile.
3. أمر التثبيت `npm ci`، وأمر البناء `npm run build:all`. في لوحة النشر الحالية اختر Build command = `npm run build` وOutput directory = `.` وEntry file = `server.js`. نقطة الدخول الجذرية تستخدم dynamic import، لأن مشغّل LiteSpeed يحمل الملف عبر require؛ الاستيراد المباشر لملف يحوي top-level await يوقف الخدمة.
4. أضف متغيرات `.env.example` في إعدادات التطبيق: `NODE_ENV=production` و`HOST=0.0.0.0` و`PORT=3000` و`COOKIE_SECURE=true` و`TRUST_PROXY=true` و`ALLOWED_ORIGINS=https://alarabiye.com,https://www.alarabiye.com`. اضبط URL القاعدة من بيانات hPanel، مع ترميز كلمة المرور داخل URL. الاتصال البعيد الذي اختُبر يستخدم اسم الخادم الموثّق و`?ssl=true`؛ إذا كانت الاستضافة توفر اتصالًا داخليًا بـlocalhost استخدم إعدادها الفعلي. لا تضع URL في متغير يبدأ بـVITE.
5. احتفظ بنفس `SESSION_SECRET` و`TOTP_ENCRYPTION_KEY` الحاليين. الإعداد الجاهز موجود محليًا في `.env.hostinger` وهو مستبعد من Git. أدخل قيمه في إعدادات التطبيق دون رفعه داخل ZIP أو عرضه في صفحة. لا تولّد مفاتيح عند كل تشغيل.
6. نفّذ migrations كخطوة مستقلة **قبل** تشغيل الإصدار: `npm run db:migrate` ثم `npm run db:audit:protect`. القاعدة الحالية اجتازت هاتين الخطوتين بالفعل. لا تستخدم `migrate reset` أو `db push --accept-data-loss`.
7. وجّه الدومين للتطبيق وفعّل HTTPS. يقدم Fastify المتجر `/` والإدارة `/admin/` والخدمات `/api/`. احتفظ بمجلدي `dist` و`admin/dist` مع `server/dist`؛ لا ترفع ملف الخادم وحده. لا تشغّل Vite في الإنتاج.
8. تحقق من `/api/health` (يعيد `status` فقط)، وافتح رابط منتج والإدارة مباشرة وأعد تحميلهما. اختبر الدخول والحفظ وظهور المنتج المنشور عبر HTTPS. نجاح إعداد القاعدة لا يثبت نجاح نشر الموقع؛ هذه الخطوة ما زالت مطلوبة على الاستضافة.

## الصور والتحديث

لم نجد ضمانًا موثّقًا لبقاء مجلد uploads الخاص بتطبيق Node.js بعد إعادة النشر، لذلك تُخزن الصور المعاد ترميزها إلى WebP داخل MySQL، لا داخل مجلد البناء. الحد 4MB للملف الداخل، و24 مليون بكسل، و1600 بكسل لأبعاد الخرج. يتم التحقق من MIME والمحتوى وتوليد المعرّف في الخادم. النسخ الاحتياطي يشمل الصورة والبيانات معًا؛ هذا مناسب لعدد المنتجات القليل، ويستهلك حصة قاعدة البيانات. الصور بقيت عند إعادة إنشاء الخادم في اختبار التكامل، وعند استعادة SQL في قاعدة مستقلة؛ إعادة نشر تطبيق Hostinger نفسه لم تُختبر بعد.

## النسخ الاحتياطي والاستعادة

```sh
npm run db:backup
RESTORE_DATABASE_URL='mysql://user:password@host/new_empty_database' npm run db:restore -- .backups/backup.sql
```

في PowerShell عيّن المتغير عبر `$env:RESTORE_DATABASE_URL`. الاستعادة ترفض أي قاعدة غير فارغة. أنشئ قاعدة جديدة واختبرها قبل تحويل التطبيق إليها. احتفظ بالأسرار الثابتة في مخزن خاص منفصل مع النسخ، لأن SQL وحده لا يكفي لفك بيانات TOTP. يحتاج السكربت `mysqldump` و`mysql` محليًا؛ يمكن تحديد `MYSQL_CLIENT_BIN`، و`MYSQL_SSL_CA` لشهادة CA مخصصة. عند الاتصال البعيد تُفرض TLS والتحقق من الهوية؛ يولّد السكربت حزمة شهادات Node العامة محليًا عند عدم تحديد CA.

لتشغيل المهام على القاعدة الحالية من هذا الجهاز: `node scripts/admin/hostinger-db.mjs db:backup` أو `db:verify`. السكربت يحمّل الإعداد الخاص دون طباعة أسراره. النسخ في `.backups` خاصة ولا تدخل Git. تم اختبار استعادة نسخة Hostinger في قاعدة محلية جديدة مع حساب المالك والصور وحماية التدقيق.

تم تصدير PostgreSQL السابق إلى JSON في معاملة قراءة متسقة، ثم نقل حساب المالك وسجل العمليات. `db:legacy:import` يرفض بيانات الأعمال غير الفارغة غير المدعومة بدل إسقاطها. migrations PostgreSQL محفوظة للأرشفة؛ المسار النشط `server/prisma/mysql-migrations`. أداة `db:migrate:repair` معالجة محددة للإعداد الأول الذي اصطدم بقيود CHECK في MariaDB 11.8؛ ليست أمر تحديث دوري.

## التحقق المسجل

- 109 اختبارات وحدة و43 اختبار تكامل على MariaDB حقيقي، بقاعدة عشوائية مستقلة تُنشأ وتُحذف للاختبار فقط.
- 6 اختبارات واجهة الإدارة بالعربية والإنجليزية وRTL والمظهرين على 360 و1280 بكسل، باستخدام `PLAYWRIGHT_CHANNEL=chrome` في الجهاز الحالي.
- البناء الكامل وفحص الأنواع وlint؛ فحص npm في 3 أكتوبر أظهر 5 تنبيهات high في سلسلة أدوات Tailwind/braces الخاصة بالبناء؛ الإصلاح المقترح آليًا ترقية رئيسية لـTailwind، ولم تُطبق أثناء إصلاح الاستضافة.
- تحقق مباشر من Hostinger: الصور موجودة، المنتجات التوضيحية المنشورة عشرة، التدقيق يمنع UPDATE وDELETE، والاستيراد المتكرر لا يكرر المنتجات.

تحذيرات البناء الحالية تخص أمثلة JSON القديمة وتراخيص صورها وحجم حزم الواجهات. المتجر لا يستخدم أمثلة JSON كبديل عند تعطل API. صفحات المتجر تعتمد JavaScript لعرض المحتوى؛ لا يوجد SSR للمحتوى المتغير في هذه المرحلة.
